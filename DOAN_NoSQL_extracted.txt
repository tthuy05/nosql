DANH MỤC TỪ VIẾT TẮT
STT
Từ viết tắt
Tên đầy đủ
Ý nghĩa
1
NoSQL
Not Only SQL
Hệ quản trị cơ sở dữ liệu phi quan hệ, tối ưu cho tốc độ và khả năng mở rộng quy mô lớn. 
2
GUI
Graphical User Interface
Giao diện đồ họa người dùng giúp trực quan hóa thao tác quản trị. 
3
CLI
Command Line Interface
Giao diện dòng lệnh tương tác trực tiếp với máy chủ. 
4
FIFO
First In, First Out
Nguyên lý vào trước - ra trước trong cấu trúc hàng đợi (Queue). 
5
TTL
Time To Live
Thời gian tồn tại (thời gian sống) của một khóa trước khi tự động hết hạn và bị xóa khỏi bộ nhớ. 
6
RDB
Redis Database 
Cơ chế lưu snapshot dữ liệu Redis tại một thời điểm xuống tệp trên ổ đĩa.
7
AOF
Append Only File
Cơ chế sao lưu ghi nối nhật ký mọi thao tác ghi dữ liệu của Redis. 
8
CRUD
Create, Read, Update, Delete
Bốn thao tác cơ bản trên dữ liệu: Tạo mới, Đọc/Truy vấn, Cập nhật và Xóa. 
9
RDBMS
Relational Database Management System
Hệ thống quản trị cơ sở dữ liệu quan hệ truyền thống (MySQL, SQL Server, PostgreSQL). 
10
API
Application Programming Interface
Giao diện lập trình ứng dụng cho phép các hệ thống giao tiếp với nhau. 
11
DLQ
Dead Letter Queue
Hàng đợi chứa các thông điệp/đơn hàng lỗi không thể xử lý thành công, dùng để cách ly phục vụ kiểm tra. 
12
SSL / TLS
Secure Sockets Layer / Transport Layer Security
Giao thức mã hóa bảo mật tầng truyền tải, bảo vệ luồng dữ liệu khi kết nối từ xa. 
13
ZSet
Sorted Set
Cấu trúc tập hợp sắp thứ tự theo điểm số (score) trong Redis. 
14
RAM
Random Access Memory
Bộ nhớ truy xuất ngẫu nhiên, nơi Redis lưu trữ và thực thi các thao tác đọc ghi dữ liệu. 
15
JSON
JavaScript Object Notation
Định dạng trao đổi dữ liệu dạng văn bản gọn nhẹ, có cấu trúc.

LỜI MỞ ĐẦU
Trong những năm gần đây, các hệ quản trị cơ sở dữ liệu NoSQL ngày càng được sử dụng trong các hệ thống yêu cầu tốc độ xử lý cao và khả năng mở rộng linh hoạt. Trong đó, Redis là một hệ quản trị cơ sở dữ liệu lưu trữ dữ liệu chủ yếu trên bộ nhớ, hỗ trợ nhiều cấu trúc dữ liệu như String, Hash, List, Set và Sorted Set. Nhờ đặc điểm truy xuất nhanh và hỗ trợ nhiều kiểu dữ liệu, Redis được sử dụng trong nhiều bài toán như lưu trữ bộ nhớ đệm, quản lý phiên đăng nhập, hàng đợi xử lý và các hệ thống thời gian thực. 
Trong quá trình quản trị Redis, việc thao tác hoàn toàn bằng dòng lệnh có thể gây khó khăn khi cần quan sát nhiều khóa và cấu trúc dữ liệu. P3X Redis UI là một công cụ giao diện đồ họa hỗ trợ người dùng kết nối, quản lý và thao tác trực quan với dữ liệu trên Redis. Vì vậy, nhóm lựa chọn tìm hiểu P3X Redis UI và áp dụng công cụ này vào bài toán quản lý hàng đợi xử lý đơn hàng trực tuyến.
Nội dung báo cáo tập trung vào việc tìm hiểu và cài đặt P3X Redis UI, khảo sát các chức năng chính của công cụ, so sánh với RedisInsight, thiết kế cơ sở dữ liệu Redis cho bài toán quản lý hàng đợi đơn hàng, thực hiện tạo dữ liệu và các truy vấn cơ bản, nâng cao, đồng thời tìm hiểu các phương pháp import, export, backup và restore dữ liệu.
TỔNG QUAN VỀ REDIS
1.1. Giới thiệu và cài đặt P3X Redis UI
1.1.1. Khái niệm và kiến trúc tổng quan 
Khái niệm: P3X Redis UI (tên gói: p3x-redis-ui) là một công cụ đồ họa mã nguồn mở (Open-source Web & Desktop GUI) dùng để quản trị, duyệt và thao tác trên cơ sở dữ liệu Redis.
Kiến trúc công nghệ:
Backend: Được xây dựng trên nền tảng Node.js và Express, sử dụng thư viện ioredis hỗ trợ kết nối Redis Cluster, Sentinel và máy chủ Standalone.
Frontend: Được xây dựng bằng Angular kết hợp với Material Design, cung cấp giao diện đồ họa giúp người dùng quản lý và thao tác với dữ liệu Redis trực quan trên trình duyệt.
Phân phối: P3X Redis UI có thể được sử dụng dưới dạng ứng dụng Desktop hoặc triển khai dưới dạng Web Server/Docker Service. Việc triển khai tập trung trên máy chủ cho phép nhiều người dùng truy cập giao diện quản trị thông qua trình duyệt.
1.1.2. Hướng dẫn cài đặt và thiết lập kết nối
Cách 1: Triển khai qua Docker (Khuyên dùng cho Web UI tập trung)
Chạy P3X Redis UI dưới dạng Docker container kết nối với mạng Redis cục bộ:
Bash
docker run -d \
  --name p3x-redis-ui \
  -p 7843:7843 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  patrikx3/p3x-redis-ui
Truy cập qua trình duyệt tại địa chỉ: http://localhost:7843.
Cách 2: Cài đặt và chạy qua NPM (Node.js)
Yêu cầu máy đã cài Node.js (>= 18):
Bash
# Cài đặt global package
npm install -g p3x-redis-ui --unsafe-perm=true --allow-root
# Khởi chạy dịch vụ
p3x-redis-ui
Giao diện Web sẽ lắng nghe tại cổng 7843.
Cách 3: Cài đặt bản Desktop App (.exe trên Windows)
Tải bản release mới nhất (p3x-redis-ui-setup-x.x.x.exe) từ kho lưu trữ GitHub chính thức của dự án (patrikx3/redis-ui).
Tiến hành cài đặt và chạy ứng dụng độc lập trên máy tính.

1.2. Chi tiết các chức năng chính của P3X Redis UI
1.2.1. Phân hệ quản lý kết nối 
Phân hệ quản lý kết nối đóng vai trò là cổng giao tiếp trung tâm của P3X Redis UI, cho phép người quản trị cấu hình, lưu trữ và duy trì đồng thời nhiều phiên làm việc tới các máy chủ Redis khác nhau trong cùng một giao diện điều khiển. Công cụ cung cấp khả năng tương thích toàn diện với nhiều mô hình kiến trúc phân tán thực tế, từ các phiên bản máy chủ cục bộ độc lập (Standalone) phục vụ quá trình phát triển, đến các cụm phân tán phức tạp như mô hình giám sát chịu lỗi Redis Sentinel và mô hình phân mảnh quy mô lớn Redis Cluster. Đối với từng kết nối, người dùng có thể cấu hình chi tiết các thông số mạng bao gồm địa chỉ IP, cổng lắng nghe (mặc định 6379), thiết lập mật khẩu bảo mật thông qua cơ chế requirepass, cũng như tích hợp các giao thức bảo mật tầng truyền tải SSL/TLS để đảm bảo an toàn cho luồng dữ liệu khi kết nối từ xa.
Hình 1.5: Danh sách kết nối Redis được quản lý trên P3X Redis UI
1.2.2. Trình duyệt khóa theo cấu trúc cây 
P3X Redis UI cung cấp cơ chế tổ chức và hiển thị các khóa dữ liệu theo cấu trúc cây. Các tiền tố của khóa được phân tách dựa trên ký tự hai chấm (:), từ đó giúp các khóa có liên quan được nhóm thành những nhánh logic. Đối với bài toán quản lý đơn hàng, các khóa như order:1001, order:1002 và queue:orders:pending có thể được tổ chức thành các nhóm tương ứng, giúp người dùng dễ dàng quan sát và tìm kiếm dữ liệu.
Hình 1.6: Trình duyệt các khóa Redis theo cấu trúc cây trên P3X Redis UI
1.2.3. Thao tác và biên tập dữ liệu đa cấu trúc
P3X Redis UI cung cấp giao diện đồ họa cho phép người dùng thực hiện các thao tác tạo mới, truy vấn, cập nhật và xóa dữ liệu (CRUD) trên nhiều cấu trúc dữ liệu của Redis như String, Hash, List, Set và Sorted Set. Đối với kiểu dữ liệu Chuỗi (String), giao diện cho phép nhập và chỉnh sửa văn bản thô, mã hóa nhị phân hoặc chuỗi cấu trúc JSON với tính năng tự động định dạng và kiểm tra lỗi cú pháp. Đối với cấu trúc Bảng băm (Hash), công cụ trực quan hóa toàn bộ danh sách các cặp trường và giá trị (field-value), hỗ trợ thêm mới hoặc cập nhật từng trường riêng biệt mà không làm gián đoạn toàn bộ đối tượng. Đặc biệt, đối với các cấu trúc phục vụ hàng đợi như Danh sách (List), Tập hợp (Set) và Tập hợp có thứ tự (Sorted Set), P3X Redis UI hiển thị chi tiết từng phần tử kèm theo chỉ số vị trí hoặc điểm số ưu tiên (score), đồng thời cho phép chèn hoặc xóa phần tử ở cả hai đầu danh sách một cách thuận tiện để phục vụ quá trình kiểm thử các giải thuật hàng đợi.

2.3. Thiết kế chi tiết các cấu trúc dữ liệu NoSQL Redis
2.3.1. Cấu trúc Hash
Lý do lựa chọn: Thay vì lưu cả chuỗi JSON vào kiểu String thông thường đòi hỏi phải phân tích toàn bộ chuỗi khi muốn đọc hoặc cập nhật một thông tin nhỏ, kiểu dữ liệu Hash của Redis ánh xạ các cặp trường và giá trị tương tự như một bản ghi trong bảng cơ sở dữ liệu quan hệ. Nó cho phép đọc và cập nhật độc lập từng trường dữ liệu với thời gian xử lý hằng số tức thì.
Cấu trúc các trường dữ liệu: order_id, customer_id, customer_name, items, total, payment_method, status, created_at, priority.
2.3.2. Cấu trúc List
Lý do lựa chọn: Kiểu dữ liệu List trong Redis được cài đặt dưới dạng danh sách liên kết đôi. Thao tác thêm vào đầu bằng lệnh LPUSH và lấy ra ở cuối bằng lệnh RPOP hoặc LMOVE đều có hiệu năng xử lý cao, phù hợp với mô hình hàng đợi vào trước ra trước.
Mô hình hàng đợi tin cậy: Trong kịch bản thực tế, nếu tiến trình xử lý dùng lệnh RPOP để lấy đơn hàng ra khỏi hàng đợi pending, đơn hàng sẽ lập tức biến mất khỏi Redis. Nếu tiến trình bị mất điện hoặc gặp lỗi ngay sau đó, đơn hàng sẽ vĩnh viễn bị mất. Để giảm nguy cơ mất dữ liệu, hệ thống áp dụng lệnh nguyên tử LMOVE chuyển đơn từ pending sang processing trong một thao tác duy nhất. Chỉ khi xử lý thành công, đơn hàng mới được xóa khỏi processing bằng lệnh LREM.
2.3.3. Cấu trúc Sorted Set
Cấu trúc Sorted Set lưu trữ các phần tử duy nhất đi kèm với một điểm số thực. Redis tự động sắp xếp các phần tử theo thứ tự điểm số.
Ứng dụng thực tế: Phần tử lưu mã đơn hàng, điểm số lưu mức độ ưu tiên. Điểm càng cao thì quyền ưu tiên xử lý càng lớn. Tiến trình xử lý chuyên dụng sẽ gọi lệnh ZPOPMAX để luôn lấy đơn có điểm cao nhất ra giải quyết trước.
2.3.4. Cấu trúc Set
Kiểu dữ liệu Set lưu trữ tập hợp các chuỗi không trùng lặp, phục vụ tra cứu hiệu quả danh sách đơn hàng đã mua của từng khách hàng với tốc độ tức thì.
2.3.5. Cấu trúc String kết hợp thời gian sống
Khóa giữ chỗ thanh toán: Khi khách hàng tiến hành thanh toán, hệ thống thiết lập một khóa tạm thời với thời gian sống 15 phút. Nếu sau 15 phút khách hàng không hoàn tất giao dịch, Redis sẽ tự động tiêu hủy khóa này để giải phóng hàng tồn kho cho khách hàng khác mua.
Bộ đếm thống kê nguyên tử: Sử dụng lệnh INCR hoặc INCRBY để tăng số lượng đơn tự động, đảm bảo tính nguyên tử khi cập nhật bộ đếm, giúp hạn chế vấn đề tranh chấp khi có nhiều yêu cầu đồng thời.

3.3. Triển khai các truy vấn cơ bản
1.  Kiểm tra số lượng phần tử hiện diện trong danh sách chờ:
LLEN queue:orders:pending# Kết quả phản hồi: 5
Đọc toàn bộ danh sách mã đơn hàng đang nằm trong hàng đợi:
LRANGE queue:orders:pending 0 -1# Kết quả phản hồi danh sách các mã từ 1005 đến 1001
Lấy toàn bộ thông tin các trường của đơn hàng 1002:
HGETALL order:1002# Kết quả phản hồi đầy đủ các cặp trường và giá trị của đơn hàng 1002
Kiểm tra thời gian tồn tại còn lại của khóa thanh toán đơn 1004:
TTL checkout:lock:1004# Kết quả phản hồi số giây còn lại trước khi khóa tự động bị xóa
3.4. Triển khai các truy vấn nâng cao cho nghiệp vụ hàng đợi
Kịch bản 1: Xử lý theo cơ chế hàng đợi tin cậy
Khi tiến trình nền sẵn sàng tiếp nhận công việc, hệ thống thực hiện thao tác dịch chuyển nguyên tử đơn hàng lâu nhất từ hàng đợi chờ sang hàng đợi đang xử lý:
LMOVE queue:orders:pending queue:orders:processing RIGHT LEFT# Giá trị phản hồi: 1004
Hình 3.6: Trực quan hóa cơ chế chuyển đơn hàng sang hàng đợi đang xử lý bằng lệnh nguyên tử LMOVE
Sau khi đơn hàng được đưa vào hàng đợi đang xử lý, tiến trình tiến hành cập nhật trạng thái đơn hàng:
# Cập nhật trạng thái trong Hash sang PROCESSING
HSET order:1004 status "PROCESSING" updated_at "2026-09-27 10:25:00"
# Cập nhật trạng thái hoàn thành và lưu mã vận đơn sau khi đóng gói thành công
HSET order:1004 status "COMPLETED" tracking_code "VNPOST_8839219" finished_at "2026-09-27 10:26:30"
# Xóa đơn 1004 khỏi hàng đợi đang xử lý
LREM queue:orders:processing 1 "1004"
Kịch bản 2: Xử lý đơn hàng ưu tiên
Tiến trình chuyên phục vụ khách hàng VIP sẽ lấy đơn có điểm ưu tiên cao nhất ra xử lý:
# Truy vấn đơn hàng có điểm ưu tiên cao nhất mà không xóa khỏi hàng đợi
ZREVRANGE queue:orders:priority 0 0 WITHSCORES
# Kết quả: đơn 1004 với điểm số 5
# Lấy ra và xóa trực tiếp đơn hàng VIP cao nhất
ZPOPMAX queue:orders:priority 1
# Kết quả: đơn 1004 với điểm số 5
# Gán đơn VIP cho chuyên viên hỗ trợ riêng
HSET order:1004 status "VIP_PROCESSING" assigned_agent "AGENT_VIP_01"
Kịch bản 3: Xử lý đơn lỗi và Hàng đợi thư chết
Nếu một đơn hàng trong quá trình xử lý gặp sự cố nghiêm trọng như tài khoản thanh toán không hợp lệ hoặc quá số lần gọi cổng ngân hàng thất bại:
# Xóa đơn khỏi hàng đợi đang xử lý
LREM queue:orders:processing 1 "1003"
# Đẩy vào hàng đợi lỗi Dead Letter Queue để nhân viên xử lý thủ công
LPUSH queue:orders:dead_letter "1003"
# Cập nhật lý do lỗi vào đơn hàng
HSET order:1003 status "FAILED_PAYMENT" error_reason "Giao dich thanh toan bi tu choi" retry_count "3"
Hình 3.7: Hàng đợi đơn lỗi Dead Letter Queue
Kịch bản 4: Truy vấn lịch sử đơn hàng của khách hàng
# Liệt kê tất cả các mã đơn hàng mà khách hàng CUST_01 đã đặt:
SMEMBERS customer:CUST_01:orders
# Kết quả: 1001 và 1003
# Kiểm tra xem đơn hàng 1002 có phải của CUST_01 hay không:
SISMEMBER customer:CUST_01:orders "1002"
# Kết quả: 0 nghĩa là không phải
Hình 3.8: Danh sách đơn hàng thuộc sở hữu của khách hàng
SAO LƯU, PHỤC HỒI VÀ QUẢN TRỊ DỮ LIỆU
4.1. Cơ chế Sao lưu và phục hồi
4.1.1. So sánh hai cơ chế lưu trữ bền vững 
Mặc dù hoạt động trực tiếp trên bộ nhớ chính, Redis cung cấp hai cơ chế lưu trữ dữ liệu xuống đĩa cứng gồm RDB và AOF.
Bảng 4.1: So sánh đặc tính kỹ thuật giữa cơ chế RDB và AOF
Tiêu chí so sánh
Cơ chế chụp ảnh trạng thái RDB
Cơ chế ghi nhật ký thao tác AOF
Bản chất kỹ thuật
Sao chép toàn bộ không gian dữ liệu tại một mốc thời gian và ghi dạng nhị phân vào tệp lưu trữ trên đĩa
Ghi nối tiếp các câu lệnh làm biến đổi dữ liệu vào tệp nhật ký văn bản
Mức độ an toàn dữ liệu
Dữ liệu phát sinh giữa hai chu kỳ chụp ảnh có thể không được bảo toàn nếu xảy ra ngắt nguồn
Dữ liệu được ghi nhận định kỳ mỗi giây một lần, giảm thiểu nguy cơ thất thoát
Tốc độ khởi động lại
Tốc độ nạp dữ liệu nhanh do Redis chỉ cần đọc trực tiếp định dạng nhị phân vào bộ nhớ
Thời gian nạp dữ liệu lâu hơn do hệ thống phải thực thi lại tuần tự các câu lệnh trong nhật ký
Kích thước tệp lưu trữ
Tệp có kích thước nhỏ nhờ thuật toán nén nhị phân
Tệp có kích thước lớn hơn do lưu trữ toàn bộ cú pháp lệnh lịch sử
Mức độ chiếm dụng tài nguyên
Tiến trình con tạo bản sao có thể làm tăng dung lượng bộ nhớ sử dụng theo cơ chế sao chép khi ghi
Quá trình đồng bộ đĩa cứng diễn ra liên tục có thể ảnh hưởng đến thông lượng ghi tối đa
Kịch bản ứng dụng
Phù hợp cho việc lưu trữ dự phòng định kỳ và chuyển giao dữ liệu giữa các môi trường
Phù hợp cho các hệ thống yêu cầu mức độ toàn vẹn dữ liệu cao
4.1.2. Chiến lược kết hợp cơ chế lưu trữ 
Đối với bài toán tiếp nhận đơn hàng, hệ thống áp dụng cơ chế kết hợp giữa hai phương thức:
Bật chế độ ghi nhật ký AOF với cấu hình đồng bộ mỗi giây nhằm lưu vết các giao dịch đặt hàng phát sinh liên tục.
Cấu hình chụp ảnh trạng thái RDB tự động theo định kỳ phục vụ việc sao lưu phòng ngừa sự cố phần cứng.
Sử dụng tính năng nạp kết hợp: Phần đầu của tệp nhật ký được mã hóa theo cấu trúc nhị phân của RDB để rút ngắn thời gian nạp dữ liệu khi khởi động, phần cuối tiếp tục lưu các lệnh ghi mới nhất để bảo toàn dữ liệu.
4.2. Thực hành Sao lưu và Phục hồi bằng dòng lệnh
4.2.1. Thực hành sao lưu chủ động với RDB 
Thực hiện các thao tác yêu cầu chụp ảnh dữ liệu và kiểm tra tham số lưu trữ trên hệ thống:
BGSAVE LASTSAVE CONFIG GET dir CONFIG GET dbfilename
Hình 4.1: Thực thi lệnh sao lưu chủ động BGSAVE và kiểm tra mốc thời gian LASTSAVE trên Console CLI
4.2.2. Kịch bản Phục hồi dữ liệu từ tệp RDB 
Khi máy chủ gặp sự cố mất dữ liệu:
Dừng dịch vụ Redis an toàn bằng lệnh SHUTDOWN từ dòng lệnh hoặc dừng tiến trình hệ điều hành.
Sao chép tệp dump.rdb từ bản sao lưu dự phòng vào đúng đường dẫn thư mục cấu hình đã xác định.
Khởi động lại dịch vụ redis-server. Khi vừa khởi động, Redis sẽ tự động đọc tệp dump.rdb và nạp toàn bộ các cấu trúc đơn hàng và hàng đợi vào RAM.
Mở P3X Redis UI kết nối lại và kiểm tra số lượng khóa được khôi phục đầy đủ.
4.2.3. Cấu hình và Tối ưu hóa AOF 
1. Kiểm tra trạng thái ghi nhật ký AOF hiện tại
CONFIG GET appendonly
2. Kích hoạt tính năng ghi nhật ký AOF mà không cần khởi động lại dịch vụ
CONFIG SET appendonly yes
3. Kích hoạt tiến trình nén và tái cấu trúc nhật ký AOF chạy ngầm
BGREWRITEAOF
Hình 4.2: Kích hoạt cơ chế ghi nhật ký AOF và tối ưu nén tệp BGREWRITEAOF
4.2.4. Công cụ kiểm tra và sửa lỗi tệp lưu trữ 
Khi máy chủ bị ngắt điện đột ngột khiến tệp nhật ký hoặc tệp chụp ảnh dữ liệu bị lỗi cấu trúc:
Kiểm tra tệp RDB: redis-check-rdb dump.rdb
Tự động sửa chữa tệp AOF: redis-check-aof --fix appendonly.aof
4.3. Xuất và Nhập dữ liệu 
4.3.1. Thao tác trên giao diện đồ họa P3X Redis UI 
Xuất dữ liệu một khóa đơn lẻ: 
Trên cây khóa bên trái, chọn khóa cần trích xuất thông tin như order:1001.
Trên màn hình hiển thị dữ liệu bên phải, chọn chế độ xem JSON View hoặc Raw View.
Bấm nút sao chép hoặc tải về để lưu cấu trúc đối tượng ra tệp văn bản định dạng JSON.
Nhập dữ liệu trực quan: 
Trên thanh công cụ trên cùng của P3X Redis UI, bấm nút Add Key.
Nhập tên khóa mới, chọn kiểu dữ liệu tương ứng như Hash hoặc List.
Nhập các cặp trường và giá trị tương ứng rồi nhấn Save để lưu dữ liệu tức thì.
Hình 4.3: Chức năng xuất dữ liệu đối soát ra định dạng JSON trên giao diện P3X Redis UI
4.3.2. Sao chép và Di chuyển khóa bằng lệnh DUMP và RESTORE 
Redis cung cấp cơ chế tuần tự hóa nhị phân độc lập cho từng khóa:
1. Trích xuất chuỗi nhị phân tuần tự hóa của đơn hàng 1001
DUMP order:1001
2. Phục hồi chuỗi tuần tự hóa sang một khóa bản sao mới với thời gian sống vĩnh viễn
RESTORE order:1001:copy 0 "\x0f\x11\x00\x00\x00..."
4.3.3. Xuất hàng loạt khóa bằng dòng lệnh Shell 
Để trích xuất danh sách tất cả các đơn hàng đang có trong hệ thống ra tệp văn bản phục vụ báo cáo đối soát:
bash
redis-cli --scan --pattern "order:*" > danh_sach_don_hang.txt
